# Architecture

polyvm is bash. There is no compiled binary and no daemon. It targets bash 3.2
so it runs on the bash that ships with macOS.

## Layout

```
~/.polyvm/
├── bin/polyvm              the CLI, and the only entry point
├── lib/                    core, util, version, plugin, compat, shim, install
├── completions/            bash and zsh completions
├── contrib/plugins/        plugins that ship with polyvm, currently python
├── polyvm.sh               shell integration, sourced from .bashrc / .zshrc
│
├── plugins/<lang>/         a cloned plugin repo, one per language
├── installs/<lang>/<ver>/  the actual runtimes
├── downloads/<lang>/<ver>/ scratch space during install, cleaned afterwards
├── shims/                  one stub per executable, this is what goes on PATH
├── compat/asdf             translating shim for plugins that call asdf
├── cache/                  plugin scratch, such as the python-build checkout
├── plugin-index/           cached clone of the asdf plugin index
└── versions                the global version file
```

Source and data can be split. `POLYVM_DIR` points at the source, `POLYVM_DATA_DIR`
at the data. They are the same directory unless you set them apart, which is what
a distro package would do.

## The pieces

| File | Responsibility |
|---|---|
| `lib/core.sh` | Paths, logging, name and version validation |
| `lib/util.sh` | Platform detection, download, checksum, safe removal |
| `lib/version.sh` | Reads version files, resolves which version applies |
| `lib/plugin.sh` | Adds, lists, updates and removes plugins, runs their hooks |
| `lib/install.sh` | Turns a version spec into an installed runtime |
| `lib/shim.sh` | Generates shims and dispatches through them |
| `lib/compat.sh` | Generates the `asdf` translation shim |
| `contrib/plugins/` | First-party plugins, found before the asdf index |
| `bin/polyvm` | Argument parsing and dispatch, nothing else |

## Version resolution

`polyvm_resolve_version_var <plugin>` sets `POLYVM_RESOLVED_VERSION` and
`POLYVM_VERSION_SOURCE`, checking in order:

1. `POLYVM_<PLUGIN>_VERSION` in the environment, which is what `polyvm shell` sets
2. `ASDF_<PLUGIN>_VERSION`, for compatibility
3. the nearest `.polyvm-versions` walking up from `$PWD`
4. the nearest `.tool-versions` walking up from `$PWD`
5. a legacy file such as `.python-version`, unless `POLYVM_LEGACY_VERSION_FILE=no`
6. the global file, `$POLYVM_DATA_DIR/versions`

A line can list several versions. The first one that is actually installed wins:

```
nodejs 22.14.0 20.18.1
```

These functions assign rather than print on purpose. A command substitution runs
in a subshell, so a printing version would throw away the source that the
`polyvm current` output depends on.

## How a shim works

`polyvm install nodejs 22.14.0` runs the plugin's install hook, then scans the
version's bin directories and writes one stub per executable:

```bash
#!/usr/bin/env bash
# Generated by polyvm. Do not edit; run `polyvm reshim` instead.
# polyvm-plugin: nodejs 22.14.0
export POLYVM_DIR="${POLYVM_DIR:-/home/you/.polyvm}"
export POLYVM_DATA_DIR="${POLYVM_DATA_DIR:-/home/you/.polyvm}"
exec "/home/you/.polyvm/bin/polyvm" exec-shim "node" "$@"
```

The `# polyvm-plugin:` lines are provenance. When several plugins ship a command
with the same name, the stub lists all of them and the dispatcher picks the one
whose version resolves in the current directory.

`polyvm exec-shim node ...` then:

1. reads the provenance lines to find candidate plugins
2. resolves the version for each until one applies
3. sources the plugin's `exec-env` hook and puts its bin dirs on `PATH`
4. `exec`s the real binary

Because the stub is a real file on `PATH`, this works in a cron job, a Makefile
or an editor's integrated terminal. Nothing has to source `polyvm.sh` first.

`system` as a version makes the shim fall through to whatever is on `PATH`
outside polyvm.

## Shell integration

`polyvm.sh` does three things: puts `shims/` on `PATH`, exports `POLYVM_DIR`,
and defines a `polyvm` shell function.

The function exists for one command. `polyvm shell nodejs 20.18.1` has to change
the current shell's environment, and a child process cannot do that. The function
calls `polyvm shell-env`, which prints an export line, and evals it. Every other
command goes straight through to `bin/polyvm`.

polyvm works without the integration. You lose `polyvm shell` and completions,
nothing else, as long as `shims/` is on `PATH`.

## Safety

- Plugin names are validated before they become directory names.
- `polyvm_safe_rm_rf` refuses any path outside `$POLYVM_DATA_DIR` and any path
  containing `..`, so a hostile plugin name cannot walk out of the data dir.
- A failed install removes its own half-written directory.
- Shims never shadow `polyvm` itself.
